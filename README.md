## Local checks

Serve the repository over HTTP (for example, `python3 -m http.server 8000`), then open `http://localhost:8000/`. The renderer supports both root hosting and a repository subdirectory. Opening HTML through `file://` will not load the JSON reliably.

Run `node --test tests/validation.test.mjs` and `node --check assets/app.js`. The dependency-free tests simulate Apps Script services; they do not certify a live Google deployment.

## Lead handler configuration

Submission is intentionally disabled while `lead_endpoint` in `data/parts.json` is `null`. No endpoint, operator inbox or production site URL was supplied, so none is invented.

1. Create a standalone Google Apps Script project and copy in `backend/Code.gs`.
2. In **Project Settings → Script properties**, set `SITE_BASE_URL` to the actual HTTPS directory URL of this site, including its repository subdirectory if any; set `NOTIFICATION_EMAIL` to the operator's single notification address. Do not put credentials in the repository.
3. Ensure the deployment owner can edit spreadsheet `16IcDQZ9omcNJaIzrkCXfK53N--qwcxhR5QQuS5P1-Ts` and send Gmail. The existing tab must be named `Leads`.
4. The expected header row is exactly:

   ```text
   timestamp, sku, machine_model, part_number, email, preference, notes, page_url, lead_status, owner_minutes, quoted, paid, estimated_contribution, actual_contribution
   ```

   The handler initializes headers only if `Leads` is completely empty. It refuses a missing tab or a different column layout instead of modifying existing records.
5. Authorize Sheets and Gmail access and deploy as a web app, executing as the deployment owner, with access for the intended visitors (anonymous public forms require **Anyone**, if permitted by the account). Use the deployed `/exec` URL, not `/dev`. Set that URL as the JSON `lead_endpoint`, then commit/push that configuration. Changing Apps Script source also requires updating the deployed version.
6. Before treating collection as operational, make one explicitly labelled test request through a real SKU page. Check the exact ledger row, Gmail notification and thank-you navigation. Test a rejected request as well. No live test lead or email was generated by the local checks.

## Submission behavior

Fields are `machine_model`, `part_number`, `preference` (`oem`, `compatible`, `either`), `email`, optional `notes`, hidden `sku` and hidden canonical `page_url`. Unknown machine or part markings can be entered as `Unknown`. Existing part number is not prefilled from the requested SKU. Query strings and fragments are not stored.

The browser uses a native form POST, so it never mistakes a `no-cors` opaque response for success. The handler bounds input, rejects unexpected or duplicate fields and disallowed SKUs, validates email/preference/page attribution, removes control characters, escapes spreadsheet formulas, and appends under a script lock. Page URL is client-supplied attribution, not origin authentication or evidence of real demand.

Only after Sheets persistence succeeds does the handler return a safe success page and redirect the sandboxed content frame to `thank-you.html`. The response also includes a user-activated `_top` link for full-page navigation; automatic top-level navigation is restricted by [Apps Script HTML-service sandboxing](https://developers.google.com/apps-script/guides/html/restrictions). It does not return a configurable HTTP 302. A public thank-you URL alone is not evidence of a saved lead.

Gmail notification follows persistence. If Gmail fails, the stored request still receives success and its status becomes `new_notification_failed` where possible; inspect the ledger and execution logs and notify the operator manually. There is no automatic email to the customer. Errors expose no lead details, account identifiers or raw exceptions. The operational fields (`owner_minutes`, `quoted`, `paid`, contribution fields) start blank and require operator entry; blank means unrecorded, not zero.

## Scope and remaining activation work

No Shopify, checkout, payments, inventory purchases, supplier orders, extra SKU pages, indexing or Search Console submission is included. Pushing code or deploying a site is implementation progress, not market validation. Genuine demand and conversion require separately reviewed evidence from actual requests and ledger outcomes.

The live endpoint, production site URL, notification address, Google authorization and deployed behavior still need configuration/verification. Privacy retention and a dedicated privacy contact are explicitly unspecified in `privacy.html`; define them before enabling collection. Public form abuse controls and durable deduplication are not implemented in v0.2: repeated successful POSTs can create repeated leads, and notifications consume the owner's Gmail quota.
